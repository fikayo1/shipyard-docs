# The yard — Shipyard's dashboard

Start it with `shipyard yard` and open `http://localhost:4800`. It's a
second front door onto the same commands the CLI has — starting new work,
watching a run, resuming or landing it — from a browser instead of a
terminal. Nothing here is a separate implementation: every action the yard
takes is the exact same code path a terminal command would trigger, so the
same guardrails apply either way. The [HTTP API Reference](/api) documents
every endpoint if you want to script against the same actions directly.

The yard has three tabs — **new work**, **yard**, and **agent trail** —
plus a run's own detail page, one click deeper than the yard tab.

## New work — shape a request before it spends anything

<figure>
  <img src="/images/yard-new-work.png" alt="The new-work screen: drafts on the left, and a numbered form on the right — starting point, request, project decisions, operating envelope." />
  <figcaption>Nothing here spends money yet — you're editing a draft.</figcaption>
</figure>

This is where a request starts. It walks through the same decisions
`shipyard new`/`shipyard iterate` ask for at a terminal, as a form instead
of an interview:

1. **Starting point** — a brand-new product, or an existing repository to
   extend. Pick "existing repository" and give it a path, and the form
   shows you up front whether Shipyard found a **verified handoff** from an
   earlier accepted run against that repo (meaning it can skip
   rediscovering context) or will do bounded discovery from scratch — see
   [`shipyard iterate`](/cli) for what that handoff actually contains.
2. **Request** — what should change, in your own words, plus any local
   reference files (a mock, a screenshot) to attach.
3. **Project decisions** — topology, project kind, provider, and model.
   Leave topology blank to let intake recommend one from what you're
   asking for.
4. **Operating envelope** — budget, timeout, and autonomy tier, set before
   any model call happens rather than discovered as a surprise later.
   Advanced options (a custom verify command, concurrent bay capacity, and
   so on) are tucked under their own disclosure so the common case stays
   short.

Saving a draft here doesn't cost anything. **Starting the interview** does
— it hands your request to the model, which asks follow-up questions where
it's genuinely ambiguous (including, for an authenticated or persistent
Next.js app, an explicit question about which deployment shape you want —
see [What You Can Build](/topologies#most-everyday-requests-composed-automatically)),
then produces a reviewable specification and acceptance-criteria list. Not
happy with it? **"return to intake"** sends you back to revise the request
instead of accepting a draft you'd rather change — each pass is kept as a
version, and once you've revised at least once you can see exactly what
changed between versions before approving.

You approve an exact version before a build ever starts; nothing builds off
a spec you haven't seen. Whatever the compiled project actually needs —
`DATABASE_URL` because you asked for persistent data, `AUTH_SECRET` because
you asked for accounts, or a topology's own fixed list — is asked for right
there and goes straight into the build's process environment, never saved
into the draft, the trace, or a URL. If something required is missing,
`shipyard build` refuses to start at all — no bay, no agent, no spend —
and tells you by name what's still needed.

## Yard — every run you've started

<figure>
  <img src="/images/yard-run-grid.png" alt="The yard tab: a grid of run cards, each showing topology, a phase timeline, a status badge, cost, duration, and gate-fail or correction counts." />
  <figcaption>61 runs, newest first — click any card for its full detail.</figcaption>
</figure>

Each card is one run, and everything on it is meant to be readable at a
glance without opening anything:

- **The mini-timeline** — one row per phase owner (planner, builder,
  reviewer, acceptor, …), with a bar for how long each phase actually ran.
  A gap means that phase hasn't started yet; a bar still growing means it's
  running now.
- **The status badge** — `done` (finished clean), `held` (finished, but
  waiting on you to land it), `interrupted` (stopped before finishing —
  resumable), or a `⏸ budget paused` badge specifically for a run that hit
  its spending limit mid-phase (see below).
- **Cost, duration, gate-fail count, correction count** — a run with
  corrections isn't necessarily unhealthy; it means the harness caught
  something and fixed it in place rather than restarting. A `gate fail`
  badge with no corrections after it is the one worth opening first.
- **`resume` / `restart`** — right on the card, no need to open it first.
  `resume` re-enters an interrupted or budget-paused run where it left off;
  `restart` runs the same request again from a clean copy of the repo. See [the CLI reference](/cli) for the difference between `resume` and
  `rerun` in what each one actually reuses.

### Opening a run

Click a card for its full detail: every phase with its gates and any
corrections, the running cost, and the same `resume`/`restart`/`land`/`stop`
actions as buttons instead of CLI flags. Two things live only here:

- **A budget-paused run offers "increase budget & resume", not just
  "resume."** Clicking it shows you exactly what will be reused before you
  submit — a saved checkpoint (which phase, which attempt) if one exists
  and is still valid against the bay's current state, or a plain statement
  that none does and the phase will restart clean. You're never resuming
  blind.
- **Session support** — a small chat scoped to this one run, grounded only
  in its own recorded evidence (recent events, phase status, cost). Ask it
  what a failure meant or whether it's ready to deploy. It can propose an
  action, like a deployment plan, but never take one on its own — the
  dashboard doesn't currently expose a button to approve a proposed action
  from the browser, so that last step (and planning a Vercel deployment in
  the first place) has to go through [the HTTP API](/api#per-run-support-chat-and-deployment-approval)
  directly for now.

A run that failed acceptance shows exactly which criteria didn't pass and
the evidence for each, not just a pass/fail summary — so you know precisely
what's still wrong without digging through raw trace events.

## Agent trail — what a bay actually looks like right now

The third tab is a live map of one run's in-progress workspace: which
phase is running, which files it's changed so far, and the actual diff for
any of them — the closest thing to looking over the agent's shoulder
without reading a raw event log. Useful mid-build, when you want to see
what's being written before the run even reaches review.

## If a browser action seems to do nothing

`shipyard yard` is its own long-running process, separate from whatever
terminal you use for anything else. A Resume or Restart it spawns only has
access to environment variables that were set *before that process
started* — see [Operator Secrets](/getting-started/operator-secrets) for
the exact failure this causes and how to spot it from a run's log.
