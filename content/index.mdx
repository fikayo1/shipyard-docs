# Shipyard

Shipyard turns a plain-English request into working software. You describe
what you want; Shipyard interviews you, writes a spec, then plans, builds,
tests, reviews, and ships it — landing real commits in a real repository,
not a transcript of an agent "trying its best."

The difference from just prompting a coding agent yourself: every step in
between is run by ordinary code, not by the model. The model does the
writing, inside one bounded step at a time. Code decides what happens next,
checks the model's work against the actual filesystem and test suite before
trusting it, and writes down everything that happened so you (or anyone
else) can see exactly why a run passed, failed, or is waiting on you.

## Three ways to drive it

Pick whichever fits how you're working right now — they're the same engine
underneath, so nothing you do in one is unavailable in another.

- **The terminal.** `shipyard new "..."` then `shipyard build`. The fastest
  way to kick something off or script it. See [CLI Reference](/cli).
- **The yard — a browser dashboard.** Start it with `shipyard yard`, open
  `http://localhost:4800`. Fill in a request, watch phases run as they
  happen, resume a paused run, or land a finished one — all from a page
  instead of a terminal. See [The Yard](/dashboard).
- **An HTTP API.** The same actions as `curl` calls or from another
  program — useful for kicking off a build from CI, from a script, or from
  another agent. See [HTTP API](/api).

## The journey, once you've made a request

1. **Intake.** You describe the outcome you want. Shipyard asks follow-up
   questions where it's genuinely ambiguous, then writes a spec and a list
   of acceptance criteria — the concrete, checkable claims "done" will be
   judged against.
2. **Build.** A planner lays out the work, a builder writes it, in an
   isolated copy of the repo (a *bay*) so nothing touches your real working
   tree while it's in progress.
3. **Verify & review.** Real commands run — your test suite, a build, a
   linter — and a reviewer checks the result against the request, not just
   against whether tests happened to pass.
4. **Accept.** Every criterion from step 1 gets ruled on individually, with
   evidence — a passing test, a file that exists, a command that ran clean —
   never just an agent's say-so that it's done.
5. **Land.** A finished, accepted run either merges straight into your
   repository (if you told it that's safe) or is held for you to look at
   first — your call, made explicit up front rather than discovered after
   the fact.

You can watch this whole sequence happen live in the yard — see the
screenshot above, and [The Yard](/dashboard) for what each screen means.

## What you can count on, every run

- **Nothing is trusted on the model's word.** A claim like "I changed these
  three files" or "this test passes" is checked against the real
  filesystem and a real command exit code before anything downstream relies
  on it.
- **A mistake is corrected, not restarted.** If a check fails in a way that
  can be fixed, the same agent gets told exactly what was wrong and tries
  again in the same session — it doesn't lose its work and start over.
- **A run can't wander outside its lane.** Each step in the process is only
  allowed to touch certain files. An attempt to write somewhere it
  shouldn't is caught and rolled back, automatically.
- **Nothing vanishes if something goes wrong.** An interruption, a budget
  limit, or a crash leaves a resumable, inspectable record behind — see
  [Getting Started](/getting-started) and [The Yard](/dashboard) for how to
  pick a paused or failed run back up.
- **You decide what's safe to land unattended.** Anything outside what
  you've explicitly marked safe is held for your review before it touches
  your real repository.
