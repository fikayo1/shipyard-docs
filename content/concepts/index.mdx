# How a request becomes software

Five ideas explain everything you'll see happen after you submit a
request — in the terminal, in the yard, or over the API. In the order
they matter:

## 1. A run is a sequence of phases

A **phase** is one bounded step with one clear owner — `plan`, `build`,
`verify`, `review`, `accept`, and so on, depending on the topology. This is
exactly what the yard's mini-timeline and the agent trail's execution map
are showing you: one row or node per phase, in order, each one either
still ahead, currently running, or finished.

Each phase has a job, an owner (who's allowed to do it), and a boundary
(what it's allowed to touch — see [What You Can Build](/topologies) for how
that's enforced). Normally the run walks this list top to bottom. It can
also step **backward**: a phase that finds something fixable in an earlier
phase's output sends the run back there for a correction, instead of
failing the whole thing outright. That's the difference between a
`correction` count and a `gate fail` count on a run's card in the yard —
one means something was caught and fixed in place; the other means it
wasn't.

## 2. Every phase reports back in a fixed shape

A phase doesn't hand its work to the next one as a conversation transcript
— it reports a structured result: what changed, what it's claiming as
evidence, and a plain-language summary. The next phase reads that report,
never a replay of everything the previous agent said. This is why a
resumed or corrected run doesn't lose context the way re-explaining
something to a person from scratch would — the handoff is data, not prose.

Each phase's report also has to match a fixed set of required fields for
that kind of phase — a build reports which files changed and a commit
message; a review reports whether it approved and, if not, exactly what's
blocking approval; an acceptance reports one verdict per criterion. A
report missing a required field is rejected before it ever reaches the
next phase.

## 3. A claim is checked before anything trusts it

A phase can *say* it changed three files, or that a command passed. Code
checks that before it's believed — the files actually exist and aren't
empty, a command actually exited zero, JSON that was claimed as an
artifact actually parses. Nothing downstream ever relies on an unverified
claim. Two checks run on **every** phase, no matter what:

- **The write boundary.** The repository is compared before and after the
  phase, and anything written outside that role's declared boundary is
  rolled back — automatically, every time. See
  [What You Can Build](/topologies#why-a-builder-cant-write-everything-and-a-reviewer-cant-write-anything).
- **The budget.** Cumulative spend on the run is compared against its
  ceiling. This is the one check that behaves differently from the rest —
  see [Retries, Repair & Budget](/concepts/retries-and-budget) for what
  actually happens when a run goes over.

A topology can add more checks on top of these two — usually "does the
real test suite pass" plus, for anything riskier, a review skill's
judgment call.

## 4. Every run gets its own isolated copy of the repo

A run works in a **bay** — a real, throwaway copy of the repository, not
your actual working tree. Nothing a run does — including something that
gets caught and rolled back — ever touches the repo you started from until
you explicitly land it. See
[Reviewing & Landing](/architecture/bays-and-landing) for what "held" versus
"landed" means and how a held bay gets merged later.

## 5. Everything that happens is written down, live

Every phase starting and ending, every check, every correction, every
dollar spent — all of it lands in a durable, queryable history the moment
it happens. The yard, `shipyard runs`, and a resumed build are all reading
that exact same history — there's no separate summary being generated for
display, and no status you'd see that isn't backed by a real recorded
event. See [Trace & Recovery](/architecture/trace-and-recovery) for what's
actually recorded and exactly what a resume does and doesn't re-check.
