# Retries, repair & budget

Three different backstops kick in when something goes wrong mid-run, and
they behave differently on purpose — confusing them is exactly what caused
a real bug, described below.

## Within a phase: correction, not restart

When a check fails on a phase, the run doesn't throw the attempt away and
start over — it sends a **correction** back into the *same* agent session,
naming exactly what was wrong, and the agent tries again with full memory
of what it already knows about the codebase. This is what a `correction`
count on a run's card in the yard means, and it's bounded — a handful of
attempts, not an unlimited loop, because a correction cycle with no ceiling
is just a slower way to discover the agent can't fix this one.

If the problem was writing somewhere it shouldn't have, that out-of-bounds
change is undone *before* the correction is sent — the next attempt starts
clean, not on top of work it was never allowed to do.

## Across phases: sending work back further

Sometimes the fix belongs further back than the phase that noticed the
problem. Two situations trigger this:

- **A real check fails** — your actual test suite, for instance — and its
  output is fed back to whichever phase can act on it, so the next attempt
  is responding to what genuinely broke, not a vague "try again."
- **A phase finishes cleanly but the work genuinely isn't done yet** — a
  distinct case from a failed check: nothing the phase produced was wrong,
  it just isn't finished (an honest acceptance ruling that some criteria
  still fail, for example). This also routes back for another pass rather
  than failing the run outright.

This is also bounded, with one extra safeguard: if a repair attempt comes
back with the *identical* failure as the one before it, the run stops
immediately instead of trying again. This came from a real incident — a
Python project's check was something the builder had no way to change, and
two rounds of an agent rewriting already-correct code against an
unfixable check cost real money for nothing. Comparing each attempt's
failure to the last one closed that.

## Across the whole run: budget is a hard stop, not a retry

This is the one that looks like the other two but isn't — and treating it
like the other two shipped as a real bug before it was caught and fixed.

Going over budget looks, mechanically, like any other failed check. But
unlike a boundary violation or something merely unfinished, **there is
nothing an agent's next reply can do about money already spent.** A
correction can't un-spend it.

<Callout type="error">
  **This happened for real.** A run with a $5.00 budget crossed its ceiling
  during acceptance, got "corrected" anyway — chasing a problem that was
  mathematically guaranteed to still be there — and finished at **$7.50**.
  Roughly half of that final spend was two correction attempts that could
  never have succeeded.
</Callout>

The fix: going over budget is now checked first, on its own, before
anything else — and it stops the phase immediately rather than triggering
another paid attempt.

### A hard stop, but a recoverable one

Going over budget doesn't fail the run outright — it **pauses** it. You'll
see this in the yard as a distinct `⏸ budget paused` status, not a plain
failure. Nothing about the work already done is discarded: a checkpoint of
the agent's response is saved the moment it comes back, before the budget
check even runs — so the work you already paid for survives the pause.

<Callout type="info">
  Recover with `shipyard build --resume <run-id> --budget <higher-amount>`,
  or the yard's **increase budget & resume** button — either way, it
  shows you exactly which checkpoint (if any) it will continue from before
  you commit to the higher spend. See
  [Checkpointed resume](/architecture/trace-and-recovery#checkpointed-resume)
  for what gets validated before a checkpoint is reused, and when it's
  refused instead.
</Callout>

## The takeaway

Not every failure is the same kind of problem. Before wiring a new check
into the standard correction path, it's worth asking: can a correction
plausibly fix this, and does trying again make it better, worse, or exactly
unchanged? Budget is the one case in Shipyard today where the honest answer
is "worse, every time" — which is why it's the one check that skips
correction entirely and pauses instead.
