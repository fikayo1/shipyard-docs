# Quickstart

Three steps, in order of increasing cost: a free scripted demo, a real
request, then a real build. Everything here works the same whether you type
it at a terminal or click it in the yard (`shipyard yard`,
`http://localhost:4800`) — this page uses the terminal because it's easiest
to follow in a doc.

## 1. The demo — no API key, no cost

```bash
shipyard demo     # four bays, running in parallel
shipyard yard      # watch them at http://localhost:4800
```

The demo plays back a **scripted** agent instead of calling a real model, so
it costs nothing and touches nothing outside a throwaway directory. Its job
is to show you the harness's own behavior under a misbehaving agent —
something you can't ask a real model to do reliably on cue.

### What to expect

One of the four demo runs deliberately writes somewhere it isn't allowed to,
on its first attempt. Watching that one in the yard (or the trace) shows:

```
build  envelope_parsed    implemented scoring and adjusted the topology
build  correction_issued  wrote to a protected path — rolled back
build  envelope_parsed    reimplemented scoring, inside the boundary this time
build  phase_ended        build passed          <- second attempt, same session
```

The violation gets caught, undone, and the same agent is told exactly what
went wrong and tries again — it isn't restarted from scratch. That's the
core promise: a mistake becomes a correction, not a do-over.

The other three runs are a controlled comparison — same everything, except
one of them never violated a boundary. Both finish **green**, but they land
differently:

```
✓ boundary violation, then recovered    →  held for a human to look at
✓ never violated anything               →  merged automatically
```

Passing every check *eventually* still doesn't earn an unattended landing —
that's deliberate, and it's the thing to notice in the demo.

## 2. A real request

```bash
shipyard new "a bookmark API where I save URLs with tags"
```

Needs Claude Code installed and authenticated (`claude` on `PATH`) — or an
OpenAI-compatible provider, see [Operator Secrets](/getting-started/operator-secrets).
This interviews you about anything genuinely ambiguous, then writes
`spec.md` and `criteria.json` — the request and the checklist the finished
product will be judged against. See
[How a Request Becomes Software](/concepts) for what those two files are
for.

**Extending something that already exists, instead of starting fresh?**
Use `shipyard iterate <repo> "<what should change>"` instead of `new` — it
reads the existing repository first so the request and its criteria are
grounded in what's actually there. See
[`shipyard iterate`](/cli#shipyard-iterate-repo-intent).

## 3. A real build

```bash
shipyard build --spec spec.md --criteria criteria.json \
  --verify "pytest" --budget 5 --tier 2
```

<Callout type="warning">
  **Set `--verify` to your real test command.** Left at its default, the
  verify step is theatre — it'll pass on code that doesn't run. Shipyard
  says so out loud at startup rather than showing you a green check that
  lied.
</Callout>

Useful flags: `--topology` (usually picked automatically from
`criteria.json`), `--repo <path>` (build into an existing repo instead of a
brand-new one), `--model`, `--tier 0..3` (how much gets landed
automatically versus held for you), `--budget <usd>`. `shipyard build
--help` has the full, current list.

The build happens in its own throwaway copy of the repo, so nothing it does
can touch your real working tree while it's in progress. At lower autonomy
tiers the result is **held** for you to review rather than merged
automatically — see [Reviewing & Landing](/architecture/bays-and-landing)
and [`shipyard land`](/cli#shipyard-land-run-id).

## Watching it live

Run `shipyard yard` any time before or during a build — it reads the same
run history the build is writing to, live.

<figure>
  <img src="/images/yard-run-grid.png" alt="The yard's run grid: cards for each run showing its topology, phase progress, status badge (held, interrupted, done), cost, duration, and gate/correction counts, with resume and restart buttons." />
  <figcaption>Every run you've started, newest first — click any card for its full timeline.</figcaption>
</figure>

Each card is one run: which phases have finished (the row of green bars),
its status (`held` waiting on you, `interrupted`, or `done`), what it cost,
how long it took, and how many gate failures or corrections happened along
the way. `resume` picks an interrupted or budget-paused run back up;
`restart` runs it again from scratch. See [The Yard](/dashboard) for what
every screen and badge means.
