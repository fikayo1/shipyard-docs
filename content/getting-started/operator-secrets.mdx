# Operator secrets & environment variables

Two different kinds of environment variable show up around Shipyard, and
mixing them up is the single most common way a run wastes money or a
dashboard action silently does nothing.

## Kind 1 — what Shipyard needs to run an agent at all

If you're using the OpenAI-compatible provider (`SHIPYARD_PROVIDER=openai`,
the default — see [Model Adapters](/adapters)):

```bash
export SHIPYARD_OPENAI_BASE_URL=https://your-litellm-proxy/v1
export HERALD_API_KEY=...          # or whatever SHIPYARD_OPENAI_API_KEY_ENV names
```

If you're using the Claude Code adapter instead, it just needs `claude` on
`PATH` and already authenticated — no separate env var.

**Set these in whichever terminal will actually start the process that
runs a build.** That includes `shipyard yard` — the dashboard is its own
long-running process, so a Resume or Restart clicked in the browser only
sees whatever environment *that* terminal had when you started it. If the
dashboard was launched from a terminal that never had
`SHIPYARD_OPENAI_BASE_URL` exported, every resume/rerun it triggers fails on
startup — even while builds you run directly from another terminal work
fine.

<Callout type="error">
  This exact thing has happened for real: the dashboard said a Resume had
  started, but nothing ever showed up as running. It crashed instantly,
  before writing anything to the run's history, because the variable wasn't
  set in the dashboard's own environment — not because of a bug. The fix
  was restarting the dashboard from a terminal that had it exported.
</Callout>

If a dashboard-triggered run seems to silently do nothing, check its log —
`GET /api/run/<id>/log`, or open the run's card in the yard — before
assuming something's broken.

## Kind 2 — what the product being built needs to actually work

This is different: credentials the **software Shipyard is building**
needs at its own runtime, not credentials Shipyard itself needs. The
`release-manager` topology, for example, declares three:

```yaml
operator_secrets:
  - env: GITHUB_TOKEN
    purpose: >-
      real GitHub API access (repo read, release write) — required for
      /api/scans against a live repo, publishing, and every acceptance
      criterion that verifies real (not fake-client) GitHub behavior
  - env: GITHUB_OWNER
    purpose: owner of the target repository the running service scans/releases
  - env: GITHUB_REPO
    purpose: name of the target repository the running service scans/releases
```

`shipyard build` prints these — with a checkmark per secret — **before any
phase runs**, but doesn't block the build on them:

```
  operator secrets — needed to actually run/verify this product, not to build it:
    ✗ GITHUB_TOKEN      real GitHub API access (repo read, release write) ...
    ✗ GITHUB_OWNER      owner of the target repository the running service scans/releases
    ✗ GITHUB_REPO       name of the target repository the running service scans/releases

    3 not set yet: GITHUB_TOKEN, GITHUB_OWNER, GITHUB_REPO
    export them any time before criteria needing live credentials run.
```

That's printed once, up front, so you can go get real credentials *while
the build is running* instead of discovering the gap only when acceptance
fails on a criterion a missing token made unreachable. **This is by
design** — a criterion that needs a real, live credential says so plainly in
its own text, for example: *"Requires a real GITHUB_TOKEN and a designated
test repository — exercised by an operator with real credentials, not
simulated."* No amount of rebuilding fixes a criterion gated on credentials
that were never supplied; only supplying real, working ones does.

### An ordinary web app or API is stricter about this than release-manager is

If your request went through intake's composed path instead of a
hand-authored topology — see
[What You Can Build](/topologies#most-everyday-requests-composed-automatically)
— required values come from whichever capabilities your project actually
needs (`DATABASE_URL` for persistent data, `AUTH_SECRET` for accounts, and
so on), and they're enforced, not just printed as a reminder:

```
  awaiting operator input — no bay or agent was started:

    · DATABASE_URL (secret): Postgres connection URL for shared durable application data.
    · AUTH_SECRET (secret): High-entropy server-only signing secret for session integrity.

  Export the required values, then rerun this same build command.
  Values are intentionally not accepted in the spec, prompt, or trace.
```

If you see this, `build` stopped before starting a bay or spending
anything — export what's named and run the exact same command again. The
yard's new-work form collects these values from you at approval time
instead, before it ever submits the build — see
[The Yard](/dashboard) — so you'd only see this message driving a build
from a terminal directly.

<Callout type="warning">
  A real credential with write access (like a `GITHUB_TOKEN` scoped to
  create releases) is heavier to leave sitting in a shell profile than the
  provider variables above. Consider exporting it just in the terminal
  session you're about to build from, rather than adding it permanently to
  `~/.zshrc`.
</Callout>
