# Operator secrets & environment variables

Two different kinds of environment variable show up around Shipyard, and
mixing them up is the single most common way a run wastes money or a
dashboard action silently fails. This page exists because both have
happened for real during builds against this harness.

## Kind 1 — what Shipyard itself needs to run an agent

If you're using the OpenAI-compatible provider (`SHIPYARD_PROVIDER=openai`,
the default — see [Model Adapters](/adapters)):

```bash
export SHIPYARD_OPENAI_BASE_URL=https://your-litellm-proxy/v1
export HERALD_API_KEY=...          # or whatever SHIPYARD_OPENAI_API_KEY_ENV names
```

If you're using the Claude Code adapter instead, it needs `claude` on `PATH`
and already authenticated — no separate env var.

**These have to be set in the process that will actually spawn the build**,
not just somewhere in your terminal history. That distinction matters more
than it sounds: `shipyard yard` (the dashboard) is a *separate, long-running
process*. When you click Resume or Restart in the dashboard, it spawns a
`shipyard build`/`shipyard rerun` subprocess via `env=os.environ.copy()` —
it hands the child exactly the dashboard process's own environment, nothing
more. If the dashboard was started in a terminal that never had
`SHIPYARD_OPENAI_BASE_URL` exported, every resume/rerun it spawns will fail
with a missing-base-URL error, *even though builds run directly from another
terminal work fine* — because that other terminal has the variable and the
dashboard process doesn't.

<Callout type="error">
  This exact failure has happened for real: the dashboard reported
  `started: true` for a Resume click (the subprocess genuinely launched),
  but nothing ever showed up as running — it crashed within a fraction of a
  second, before writing a single trace event, because
  `SHIPYARD_OPENAI_BASE_URL` wasn't set in the dashboard's own process. The
  fix was restarting the dashboard from a terminal that had the variable
  exported — not a code change.
</Callout>

If a dashboard-triggered run seems to silently do nothing, check its log
first: `GET /api/run/<id>/log` (or the `.shipyard/dashboard-logs/` directory
directly) — the dashboard writes a spawned process's full stdout/stderr
there specifically so a crash-before-first-event doesn't vanish into a
subprocess nobody's terminal is attached to.

## Kind 2 — what the *product being built* needs to actually work

This is different: credentials the **delivered software** needs at its own
runtime, not credentials Shipyard needs to build it. The `release-manager`
topology, for example, declares three:

```yaml
operator_secrets:
  - env: GITHUB_TOKEN
    purpose: >-
      real GitHub API access (repo read, release write) — required for
      /api/scans against a live repo, publishing, and every acceptance
      criterion that verifies real (not fake-client) GitHub behavior
  - env: GITHUB_OWNER
    purpose: owner of the target repository the running service scans/releases
  - env: GITHUB_REPO
    purpose: name of the target repository the running service scans/releases
```

`shipyard build` prints these — with a ✓/✗ per secret — **before any phase
runs**, deliberately not blocking the build on them:

```
  operator secrets — needed to actually run/verify this product, not to build it:
    ✗ GITHUB_TOKEN      real GitHub API access (repo read, release write) ...
    ✗ GITHUB_OWNER      owner of the target repository the running service scans/releases
    ✗ GITHUB_REPO       name of the target repository the running service scans/releases

    3 not set yet: GITHUB_TOKEN, GITHUB_OWNER, GITHUB_REPO
    export them any time before criteria needing live credentials run.
```

Printed once, up front, so you can go get real credentials *while the build
is running* instead of discovering the gap only when acceptance fails on a
criterion a missing token made unreachable. **This is by design, not a bug**
— criteria that explicitly require real, live-credential verification say so
in their own text, for example: *"Requires a real GITHUB_TOKEN and a
designated test repository — this step is exercised by an operator with real
credentials, not simulated."* No amount of rebuilding fixes a criterion
gated on credentials that were never supplied; only supplying real, working
credentials does.

<Callout type="warning">
  A real credential with write access (like `GITHUB_TOKEN` scoped to create
  releases) is a heavier thing to leave sitting in a shell profile than the
  LLM-proxy variables above. Consider exporting it just in the terminal
  session you're about to run a build from, rather than adding it
  permanently to `~/.zshrc` — smaller blast radius for the same convenience,
  during active iteration.
</Callout>
